# Deploy: the microservices version on one server

Runs the whole stack (Java billing service, Node.js notifications, Python reports, React dashboard, PostgreSQL,
Redis, Kafka, Kafka UI, Mailpit) on a single small Linux server, behind HTTPS and a shared login. Built for the
**Oracle Cloud Always Free** Ampere A1 VM (free, no time limit), but it works on any Ubuntu box with **2 GB of RAM or more** (see "Memory" below).

```
internet ──443──> Caddy (HTTPS + password) ─┬─> dashboard (nginx)
                                            ├─> /api/billing ──> billing-service ──> PostgreSQL
                                            │                         └─ outbox ──> Kafka ──┬─> notification-service ──> Mailpit
                                            ├─> /api/report  ──> report-service <───────────┘        (SMTP)
                                            ├─> /kafka       ──> Kafka UI                   └──> Redis
                                            └─> /mail        ──> Mailpit
```

Only Caddy is exposed. The databases, Kafka and the services live on the private Docker network.

## Logins and the owner password

The site has real accounts: anyone can create a company (each sees only its own data), or press "Entrar como
visitante" for a private sandbox with sample data that is deleted after 24 hours. The three services verify the same
login token, signed with `JWT_SECRET` (generated by the bootstrap script). Tokens last 4 hours (`JWT_TTL_HOURS`).
A forgotten password is reset by a company administrator on the Equipe screen; the owner of the platform (or a lone
administrator) uses `bash deploy/reset-password.sh email@company.com` on the server. A company can have several users: an administrator adds the e-mail of an account created without a company.

Kafka UI (`/kafka`) and Mailpit (`/mail`) show the data of **every** company, so Caddy puts a separate password in
front of them (`visitante` and the password printed at the end of the install). Keep it private; use it when you
share your screen to show the messages flowing through Kafka.

## Steps

The detailed, click-by-click guide (Portuguese) is in [GUIA-ORACLE.md](GUIA-ORACLE.md). In short:

1. Create an Oracle Cloud account and an **Ampere A1** instance (Ubuntu 24.04, 2 OCPU / 12 GB).
2. Open ports 80 and 443 in the instance's security list.
3. Create a free name at https://www.duckdns.org pointing to the instance's public IP.
4. On the server: clone the repository and run

   ```bash
   bash deploy/oracle/bootstrap.sh your-name.duckdns.org
   ```

   It installs Docker, opens the firewall, writes `deploy/.env` (with a random `JWT_SECRET`), and builds and starts
   everything. At the end it prints the address and the owner password.

## Useful commands (on the server)

```bash
cd ~/billing-platform
DC="sudo docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml"
$DC ps                         # what is running
$DC logs -f billing-service    # follow one service
git pull && $DC up -d --build  # update to the latest code
```

## Memory (made to fit in 2 GB)

Measured with the real stack under load (about 85 simultaneous users, three rounds): Kafka ~460 MB, billing (Java)
~410 MB, PostgreSQL ~90 MB, notification ~80 MB, report ~60 MB, Mailpit ~50 MB, the rest under 20 MB each: about
**1.2 GB** in total, with no container killed or restarted. A 2 GB server also needs ~300-400 MB for the system and
Docker, so it fits with little room to spare; 4 GB is comfortable.

* Every container has a memory ceiling (`mem_limit`), so a runaway service is restarted by Docker instead of taking
  the server down, and the JVMs run with small heaps.
* **Kafka UI is off by default** (~300 MB). Turn it on to show the architecture and off afterwards:

  ```bash
  DC="sudo docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml"
  $DC --profile tools up -d kafka-ui     # then open https://your-address/kafka
  $DC stop kafka-ui
  ```

  While it is off, `/kafka` answers with a short message (and still asks for the owner password first).
* `bootstrap.sh` creates a 2 GB swap file on machines with less than 3.5 GB of RAM, as a safety net.

## Notes

* Monthly charges are issued by a job that runs every hour (`RECURRING_CRON`), 5 days before each due date.
* The overdue job runs every 10 minutes here (once a day in the base configuration) so invoices that pass their
  due date show up as overdue soon, with the events flowing through Kafka. It is idempotent.
* JVM heaps are capped (`-Xmx`) so billing, Kafka and Kafka UI fit comfortably in 4 GB.
* `deploy/.env` holds the generated database password and the password hash. It is git-ignored.
* To test it on your own machine: set `SITE_ADDRESS=http://localhost`, `HTTP_PORT=8088` in `deploy/.env` and
  open http://localhost:8088.
